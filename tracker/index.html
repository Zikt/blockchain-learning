      How a week runs

      Every block has the same shape, so you never have to plan a week. Learn from a short, fixed list, build something that runs, then write down what you understood.

      • Miss a week? Skip ahead, don't double up. Move the start date and every week's dates shift.
      • If a build runs over, cut the optional reading first, never the log.
      • Mon and Wed are flex days. Time logged there counts toward the week, so you can shorten Saturday.
      • Every Saturday ends with a push to GitHub and a proof link in the tracker. See "Build in public" below.

      What you need

      Everything except the hardware is free. Order the hardware by early November so it arrives before week 10. Prices vary a lot by seller, so check local electronics shops or AliExpress/Amazon; the required parts usually come to a few tens of US dollars.

      Build in public

      One public GitHub repo holds everything: code, notes and a progress table. Each week's folder is your proof of learning, and the commit history shows steady work. Paste each week's folder link into the Public proof field in that block.

      Routine

      1. Every session: commit before you stop, even if it's only notes. Write messages that say what happened, like week03: partition test shows a 4-block reorg.
      2. Saturday: fill in the week's README, update the progress table, push, and paste the folder link into the tracker.
      3. Each finished project: tag a release (v0.1-toy-chain, v0.3a-erc20 … v1.0-capstone).
      4. Deployed contracts: verify on Etherscan and put the address in the week's README.
      5. Optional, 15 min on Saturday: a short LinkedIn or X post linking the week's folder. The capstone gets a full write-up in week 11.

      Keep it safe

      • Never commit private keys, seed phrases or .env files. Add them to .gitignore in week 1, and store deploy keys with cast wallet import rather than in plain text.
      • Use testnet-only wallets for everything in this repo.
      • Optional: open one GitHub issue per week with that week's checklist, and close it from your last commit (closes #3). It gives each week a timestamped record.

      Habits that run alongside every phase

      • Read one exploit post-mortem on rekt.news each month, even after Phase 4.
      • Stay on regtest, Anvil and testnets. Use a separate browser profile for wallets, and never paste a seed phrase anywhere.
      • For any project you read about, ask who has to trust whom, and what still works if the chain disappears. If a trusted party already exists, a database usually wins.
      • Phase 7 moves fastest. Check the current state of any agent-payment or zkML tool before you build on it.

      Nearly every resource here is free. The books (Mastering Bitcoin, Mastering Ethereum, the Princeton textbook, Programming Bitcoin) are free to read online. Hour estimates assume you already code comfortably in Python.
